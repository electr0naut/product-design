## R1. The real board: the verbs and status names are right; two rules were not in my code
Real `hermes kanban` from the running image (2026.9.24), scratch board on a tmpfs, `--network none`, nothing mounted but the script; containers removed.
- **As assumed:** `schedule <id> <text>` works on a **claimed** (running) card and on a ready one; the status is `scheduled`; the `--status ready` list leaves it out; `unblock` returns it to `ready` and it can be claimed again; `claim` and `heartbeat` are refused while scheduled; **ten park/unpark/claim rounds** set off no counter (no `FAILED` line, card still `running`).
- **`schedule` refuses** an already scheduled card and a blocked one (exit 1). So a park that took but lost its answer would be "refused" for ever: the code now reads the card's status before counting a failure.
- **`block` refuses a scheduled card** (exit 1). The block of old is therefore possible after a refused park (card running or ready), **not** after a refused unpark.
- `unblock` is refused on a ready or running card. With an unfinished parent it returns a card to `todo`; **with a finished parent, as our review cards have, to `ready`** (test 10).
- **Dispatcher:** three ticks (one dry) left the scheduled cards alone. Limit: the scratch board has no `reviewer` profile and no gateway; the live gateway's own dispatcher was not run against a scheduled card.

## R2. What a refused park or unpark does now
- **Park refused** (in `_park`, or when parking a readied card again): the pass ends normally (`park failed <card>`), so gates still run; the next two passes try again, before anything else about that wait, even if it falls due. After the third refusal: `block --kind transient "reviewer runner failed: could not park the card: <error> (<why it was to wait>)"`, wait forgotten. The limit-start alert still goes out.
- **The board refuses the block too:** the pass still ends normally, one alert, and the block is tried again on every pass.
- **Unpark refused when due:** the pass ends normally. At the third refusal **one alert** naming the card, and `STATE.md` says "due, but the board refuses to unpark it"; it is retried every pass. No block is attempted: the board would refuse it.
- A park or unpark that took effect and reported a failure counts as done.
- Nothing lands in any of these. **The stand-in board now enforces the real rules above.** One old test expected the failing pass; it now checks only "the wait is recorded before the park", with a pass killed there.
- If the board cannot even be **listed**, a pass still fails, as every pass does today.
