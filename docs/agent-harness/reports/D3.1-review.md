## Required before any FIX Lens ticket: the host runs code that workers can edit (D5)

Reviewing the overlay change, I traced where the host runner gets its code and commands:

- `harness-reviewer.service` runs `/srv/lab/agent-harness/.venv/bin/python -m harness.reviewer` with
  `WorkingDirectory=/srv/lab/agent-harness`. So the **host** imports `src/harness/*.py` from `/srv/lab`.
- `harness.host.toml`, which holds `prove_cmd` and `gates_cmd` (commands the host executes), also lives in
  `/srv/lab`.
- `/srv/lab` is mounted into the container, and everything in it is owned by uid 1000, which is `hermes`
  in the container. Only `.venv-container` and `node_modules` are root-owned since tonight.

So any Hermes worker with a terminal (the implementer has one) can edit `reviewer.py` or `gates_cmd` and get its
commands run **on the host as `ubay`** within a minute. From there it can reach the trusted repo, the Hermes
secrets and Docker. It doesn't take an attacker: a stuck implementer "fixing" the harness config to make its
gates pass would do it. The trusted repo, the host-only ledger and the stored proofs all assume that the host's
own code is out of the workers' reach, and it isn't.

The gates in the container have the same weakness at a smaller scale. They read `harness.toml`, the overlays and
`src/` from `/srv/lab`, so a worker can change what "pass" means.

**D4 can still run tonight.** It uses only our own fixture, and the models have shown no sign of this. Do D5
straight after D4, before anything else.

### D5: what to build

1. **A host-only kit for the host runner.**
   - Make a clone of `agent-harness` at `~/.local/share/agent-harness/kit`, with its own venv. It must not be
     under `/srv/lab` or mounted into the container.
   - Check out the reviewed commit there.
   - Point the systemd unit's `ExecStart` and `WorkingDirectory` at it, and read `harness.host.toml` from it.
   - **Deploying a reviewed kit commit** becomes an explicit step: fetch, check out the sha, reinstall. Write
     the reviewed sha to a host-only file, and have the runner log it on every pass.
   - Changing the user unit is reversible, so it's approved here.
2. **The runner refuses to start from a writable place.** At startup the runner checks that its own package
   directory and its config file are not under any path the container mounts. Read the mounts once with
   `docker inspect hermes`, and pass them to the runner in config.
   - Tests: a kit path under a mounted folder refuses to start, and a host-only one starts.
3. **The container's copy of the kit is read-only to workers.** `src/`, `schemas/`, `harness.toml`, `eval/`,
   `tools/` and `template/` under `/srv/lab/agent-harness` must be root-owned, the same as the venv. `work/` stays
   writable.
   - That needs `sudo`, so it's a stop for the user. Write the exact command in the report, as one line with an
     undo.
   - From then on, deploying the kit into the container also needs `sudo`. Note that in the deploy step.
4. **Report as `D5-host-kit.md`**, with:
   - `systemctl --user cat` of the unit;
   - the runner's startup log showing the kit path and sha;
   - a test showing that an edit to `/srv/lab/agent-harness/src/harness/reviewer.py` no longer changes what the
     host runs. Use a harmless marker line, then revert it.
