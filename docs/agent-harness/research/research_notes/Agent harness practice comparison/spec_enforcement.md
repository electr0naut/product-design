## 1. How is the spec represented (structured requirements, design docs, acceptance-criteria formats like EARS, interface contracts)?

### Takeaway
The leading spec-driven tools split the spec into a fixed set of files: requirements, then design/plan, then a task list. They make requirements testable with a constrained syntax: EARS in Kiro, numbered FR-IDs and acceptance scenarios in Spec Kit. Interface contracts get their own artifact: Spec Kit has a `contracts/` output and a `data-model.md`. Cross-cutting design and domain rules go in a separate always-loaded document: Spec Kit's `constitution.md`, Claude Code's `CLAUDE.md` / `.claude/rules/`, Devin's Knowledge, and Copilot/Codex instruction files.

### Cited Findings
- **Kiro (search extract):** a spec is three files. `requirements.md` holds what the system should do, `design.md` how it will do it, and `tasks.md` the executable implementation tasks — [AWS Builder Center guide](https://builder.aws.com/content/3DWagLjqsjIIIJ9evVne8P4ZbD6/kiro-specs-stop-improvising-and-start-planning-features-with-ai); [Kiro Specs docs](https://kiro.dev/docs/specs/).
- **Kiro (search extract):** `requirements.md` "uses EARS (Easy Approach to Requirements Syntax) notation to provide structured, testable requirements". Requirements follow the form "WHEN [condition/event] THE SYSTEM SHALL [expected behavior]", which the docs call unambiguous and testable — [Kiro Feature Specs](https://kiro.dev/docs/specs/feature-specs/); [Kiro Requirements-First](https://kiro.dev/docs/specs/feature-specs/requirements-first/).
- **Kiro (search extract):** `design.md` holds the technical architecture and implementation approach. Tasks are sequenced by dependency and each one links back to requirements. Kiro offers a Requirements-First flow (Requirements, then Design, then Tasks) and a Design-First flow that derives requirements from a technical design — [Kiro Specs docs](https://kiro.dev/docs/specs/); [Kiro Feature Specs](https://kiro.dev/docs/specs/feature-specs/).
- **Spec Kit:** "The specification becomes the primary artifact." `/speckit.specify` creates a `specs/[branch-name]/` folder. `/speckit.plan` produces plan, data-model, **contracts**, research and quickstart documents. `/speckit.tasks` writes `tasks.md` from `plan.md`, marking parallel tasks `[P]` — [Spec Kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).
- **Spec Kit:** design and domain rules live in a project "constitution". "The constitution (`memory/constitution.md`) acts as the architectural DNA of the system." Sample articles include Library-First, CLI Interface (text in, JSON out), Test-First ("NON-NEGOTIABLE"), Simplicity ("Maximum 3 projects"), Anti-Abstraction ("Use framework features directly rather than wrapping them"), and Integration-First ("Contract tests mandatory before implementation"). Amendments need documented rationale, maintainer approval and a compatibility assessment — [Spec Kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).
- **Spec Kit:** ambiguity is marked inside the spec as "[NEEDS CLARIFICATION: specific question]", and the LLM is told not to guess. The spec checklist requires "No [NEEDS CLARIFICATION] markers remain", "Requirements are testable and unambiguous" and "Success criteria are measurable". Templates forbid "speculative or 'might need' features" — [Spec Kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).
- **Spec Kit:** the required implementation order is contracts first, then tests (contract, integration, e2e, unit), then source code — [Spec Kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).
- **Spec Kit (current, Oct 2026):** the README now lists `/speckit-constitution`, `-specify`, `-plan`, `-tasks`, `-implement` and a new `-converge`, plus bug-fix and idea-assessment command families. News items are dated May to Oct 2026. The repo shows about 151k stars — [Spec Kit README](https://github.com/github/spec-kit).
- **Claude Code:** the recommended way to produce a spec when requirements are unclear is to "Interview me until you could write the spec, then write it to SPEC.md". Then "start a fresh session to build from it, so the build begins with a clean context and a written definition of done. It's also the file you'll point the reviewer at later" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- **Claude Code:** `CLAUDE.md` should hold only what Claude cannot infer from code: exact test, typecheck and lint commands, plus "Decisions that aren't in the repo". Area-specific rules go in `.claude/rules/` with a `paths:` filter, so they load only when Claude is working in those paths — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- **Claude Code:** the docs separate two kinds of instruction. Non-deterministic ones are prompt, `CLAUDE.md` and skills: "there's no *guarantee* that it'll follow your instructions". Deterministic ones are hooks, deny rules and managed settings: "Claude Code applies this every time" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- **Devin (search extract):** playbooks (now being replaced by Skills; from Oct 24, 2026, new accounts start with Skills only) have a "Specifications" section of postconditions describing what must hold when Devin finishes, so it can check its own work. They also have a "Forbidden Actions" section ("anything Devin must never do") and an "Advice" section. Broad style guides and project rules belong in Knowledge or Skills — [Devin: Creating playbooks](https://docs.devin.ai/product-guides/creating-playbooks); [Devin: Skills](https://docs.devin.ai/product-guides/skills).

### Inferences
- None of the systems reviewed has a first-class interface criterion like our AC0 (exact import, call shape, result keys) attached to each ticket. The closest is Spec Kit's `contracts/` directory plus the rule that contract tests come before implementation. Our AC0 is a per-ticket version of the same idea.
- Spec Kit separates feature requirements (spec.md) from standing design and domain rules (constitution.md), and gives constitution violations top severity (section 2). That suggests our technical design's design rules could be split out and tagged MUST/SHOULD, so the conformance pass can rank findings by type.

- OpenAI Codex AGENTS.md docs (developers.openai.com) and agents.md could not be fetched. I have no primary-source detail on AGENTS.md layering or Codex "review guidelines".
- Copilot custom-instructions docs (docs.github.com) could not be fetched. Copilot details below come from github.blog changelog extracts only.
- I could not read the full Kiro requirements/design templates, so I cannot confirm whether `design.md` carries explicit interface signatures.

## 2. Is conformance checked by a separate reviewer, agent or tool after implementation? How?

### Takeaway
Yes, in most systems, and the strongest recent designs check against the spec itself, not just for generic bugs. Spec Kit has two checks. `/speckit.analyze` is a read-only cross-artifact check run before implementation. `/speckit.converge` runs after implementation: it compares the code to spec, plan and tasks, needs a source reference and evidence for each finding, and turns gaps into new tasks. Claude Code recommends a fresh, read-only reviewer subagent pointed at SPEC.md and told to "skip style". Kiro converts requirements into property-based tests. Copilot runs tests, linters, CodeQL and its own code review before opening a PR. None of these sources describes a verbatim-quote rule like ours.

### Cited Findings
- **Spec Kit `/speckit.analyze`** (before implementation): it is read-only ("Never modify files") and checks `spec.md`, `plan.md` and `tasks.md` (optionally `data-model.md`) against the constitution. Its detection passes cover Duplication, Ambiguity, Underspecification, Constitution alignment, Coverage gaps and Inconsistency, including "task-stated field constraints that contradict `data-model.md`". Any conflict with a constitution MUST principle "is automatically CRITICAL". Output is a findings table (ID, Category, Severity, Location(s), Summary, Recommendation; capped at 50 rows), plus a coverage table mapping requirement keys to tasks and metrics including coverage % — [Spec Kit analyze.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/analyze.md).
- **Spec Kit `/speckit.converge`** (after implementation): it "closes the gap between a feature's specification and what the codebase currently implements". Inputs are spec.md, plan.md and tasks.md as "the sole source of intent", the constitution, and the code named in plan and tasks. It checks tasks against code "regardless of checkbox state, since completion claims are not treated as evidence". Each finding is classified `missing`, `partial`, `contradicts` or `unrequested`, given a CRITICAL to LOW severity, and "need[s] a source reference (such as FR-003 or a plan decision) and evidence naming the file or area observed". It does not edit code. It appends a `## Phase N: Convergence` section of new tasks to `tasks.md`. The README says: "Repeat implement and converge until convergence reports `Converged`" — [Spec Kit converge.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/converge.md); [Spec Kit README](https://github.com/github/spec-kit).
- **Spec Kit:** pre-implementation "Phase -1" gates are checklists, for example the Integration-First Gate: "Contracts defined?" and "Contract tests written?". Any gate that fails must be justified in a "Complexity Tracking" section — [Spec Kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).
- **Claude Code:** the docs list four ways to check "done": in the prompt; `/goal`, where "a separate model checks against the conversation after every turn"; a `Stop` hook (exit code 2 blocks the turn from ending); and "By someone who didn't write the code: … `/code-review` reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- **Claude Code**, review against a spec: "use a subagent to review the rate limiter diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style". The docs warn: "Don't drop the `skip style` part… A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- **Claude Code:** the example reviewer subagent (`.claude/agents/reviewer.md`) has `tools: Read, Grep, Glob`, so the harness, not the prompt, stops it from editing. Its prompt is: "You're reviewing code you didn't write. Compare the changed files against the spec you're given, check that every requirement is implemented and the listed edge cases have tests, and report only the gaps that affect correctness. Skip style." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- **Claude Code:** "A `prompt` or `agent` hook asks *another model* to decide, so it isn't deterministic either. For real enforcement, use a `command`, `http`, or `mcp_tool` hook." Also: "If something has to happen every time, make it a hook… `CLAUDE.md` is for guidelines, and Claude is allowed to decide a guideline doesn't apply." Also: "ask Claude for *evidence*: the command it ran and its output" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- **Anthropic, Building Effective Agents (Dec 19, 2024):** "In the evaluator-optimizer workflow, one LLM call generates a response while another provides evaluation and feedback in a loop." It works best "when we have clear evaluation criteria". "Code solutions are verifiable through automated tests", but "human review remains crucial for ensuring solutions align with broader system requirements" — [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).
- **Copilot coding agent (search extracts of changelogs):** before opening a PR it "reviews its own changes using Copilot code review… gets feedback, iterates, and improves the patch". It runs CodeQL, checks new dependencies against the GitHub Advisory Database, and runs secret scanning (Oct 28, 2025). It runs the project's tests and linter, and these validation tools can be configured (Mar 18, 2026); they became 20% faster (Apr 10, 2026). It "cannot mark its pull requests as 'Ready for review' and cannot approve or merge" — [GitHub changelog 2025-10-28](https://github.blog/changelog/2025-10-28-copilot-coding-agent-now-automatically-validates-code-security-and-quality/); [GitHub changelog 2026-03-18](https://github.blog/changelog/2026-03-18-configure-copilot-coding-agents-validation-tools/); [GitHub changelog 2026-04-10](https://github.blog/changelog/2026-04-10-copilot-cloud-agents-validation-tools-are-now-20-faster); [Copilot coding agent docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent).
- **Kiro (search extract):** Kiro "extracts properties directly from your EARS requirements" during design and writes property-based tests (property code plus input generators) to check whether the code matches the spec. The blog is titled "Does your code match your spec?" — [Kiro blog: property-based testing](https://kiro.dev/blog/property-based-testing/); [Kiro docs: correctness](https://kiro.dev/docs/specs/correctness/).
- **Google AutoCommenter (review-side conformance to written rules):** an LLM-based system that "automatically learn[s] and enforce[s] programming language best practices", deployed to "tens of thousands of developers" in Google code review. Each comment points to a best-practice document (URL) — [Google Research: AI-assisted assessment of coding practices in industrial code review](https://research.google/pubs/ai-assisted-assessment-of-coding-practices-in-industrial-code-review/); [arXiv 2405.13565](https://arxiv.org/abs/2405.13565) (abstract via search extract; full text not fetched).

### Inferences
- Our spec-conformance pass maps most closely to Spec Kit's `/speckit.converge`. Both use spec-only intent, ignore completion claims, require a cited source per finding, and do not edit code. Two differences stand out. (a) Converge requires a requirement ID or plan-decision reference plus code evidence; ours requires a verbatim quote, which is stricter on the spec side but says nothing about code-side evidence. (b) Converge's `unrequested` category flags code the spec did not ask for, which our pass does not appear to check.
- Our second gate (a finding must be proven by a failing test before it blocks) follows the same idea as Anthropic's warning that reviewers "will always find something", and as the "skip style" instruction: it cuts down on false-positive churn. None of the sources reviewed makes test-proof a hard gate for review findings; Spec Kit converge just turns findings into tasks.
- Spec Kit runs consistency checks before implementation (`analyze`) as well as after (`converge`). Our three escaped tickets had interface and domain deviations. Some of those might be caught by checking ticket against design before implementation (does the AC0 match the technical design's interface and data model?), as `analyze` does with `data-model.md` field constraints.

### Gaps
- I found no primary source reporting precision or recall for spec-against-diff LLM reviewers like converge or the Claude reviewer subagent.
- I could not fetch Copilot code review docs to see whether its review reads the issue or spec text, or only the diff and custom instructions.
- Devin's post-implementation checking beyond "Specifications" postconditions was not confirmed from primary text.

## 3. How do they keep traceability from requirement to test to code?

### Takeaway
Traceability works through stable IDs carried through the artifacts. Kiro links each task, and each property test, to a requirement and design section. Spec Kit uses requirement keys (e.g. FR-003) in a requirement-to-task coverage table, and converge findings must cite those IDs. Spec Kit also requires a citation such as `data-model.md` + `Entity.field` on tasks that implement constrained fields. Claude Code, Copilot and Devin have no built-in ID scheme; traceability depends on how the user writes SPEC.md and the prompts.

### Cited Findings
- **Kiro (search extract):** tasks are sequenced by dependency and "link each to requirements". In generated task lists, each property test links back to its requirement and design, so a failing property can point to the spec itself — [Kiro Specs docs](https://kiro.dev/docs/specs/); [Kiro docs: correctness](https://kiro.dev/docs/specs/correctness/).
- **Spec Kit:** "Every architectural decision traces back to specific requirements." "Every feature must trace back to a concrete user story with clear acceptance criteria." "Acceptance scenarios become tests." Test scenarios are "part of the specification that generates both implementation and tests" — [Spec Kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).
- **Spec Kit `analyze`:** coverage gaps include "requirements with no tasks, tasks with no requirement… constrained fields lacking an explicit `data-model.md` + `Entity.field` citation in an implementing task". A missing field citation is HIGH severity. Output includes "a coverage summary mapping each requirement key to its tasks" and coverage % — [Spec Kit analyze.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/analyze.md).
- **Spec Kit `converge`:** findings cite a source reference "(such as FR-003 or a plan decision)" plus code evidence. New tasks get new IDs appended in a Convergence phase. "Existing IDs are never renumbered or edited" — [Spec Kit converge.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/converge.md).
- **Claude Code:** the reviewer checks that "every requirement is implemented and the listed edge cases have tests". The requirement-to-test link is checked by the reviewer, with no ID scheme built in — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).

### Inferences
- Our verbatim-quote rule gives traceability to spec text but not to a stable ID. If the ticket or design text changes, quotes may stop matching. Spec Kit pairs a requirement ID with evidence; adding IDs to ACs and design rules (e.g. AC0, AC3, DR-7) next to the quote would make coverage measurable (requirement to test to finding), as Spec Kit's coverage table does.
- Spec Kit's `Entity.field` citation rule targets the domain-field drift class of defect we saw. It is a cheap check: every task or test that touches a constrained field must cite the design's field definition.

### Gaps
- No source reports measured traceability completeness or its effect on defect escape.

## 4. How do they handle domain rules that need fixed reference examples (golden tests, examples in specs)?

### Takeaway
The main documented approach is generating tests from the spec, not pinning golden values. Kiro turns EARS requirements into property-based tests (Hypothesis, fast-check) and says example-based tests are still needed where properties don't fit. Spec Kit requires tests to fail first, contract tests and real-database integration tests before code. Claude Code advises giving the agent a concrete check to run. I found no primary source on golden or reference-value tables inside agent specs.

### Cited Findings
- **Kiro (search extract):** PBT states "a general rule" and lets a tool generate many inputs to try to break it. It "cannot guarantee the absence of all bugs" but gives stronger evidence than example-based tests alone. Recognized patterns include round-trip properties. Kiro uses Hypothesis for Python; a Kiro blog post used fast-check for TypeScript — [Kiro docs: correctness](https://kiro.dev/docs/specs/correctness/); [Kiro blog: property-based testing](https://kiro.dev/blog/property-based-testing/); [Kiro blog: PBT caught a security bug](https://kiro.dev/blog/property-based-testing-fixed-security-bug/).
- **Kiro (search extract):** "Not every requirement maps cleanly to a property". Requirements that depend heavily on external services or non-deterministic behavior "may need mocking or example-based tests". Property tests are optional by default. A community AWS Builder Center post says the feature is IDE-only — [Kiro docs: correctness](https://kiro.dev/docs/specs/correctness/); [AWS Builder Center](https://builder.aws.com/content/3J3xvomwP3iF4K7U0mFkYLyRTF5/kiro-doesnt-just-write-tests-it-proves-properties) (community post, not official docs).
- **Spec Kit:** Test-First is "NON-NEGOTIABLE". Tests must be confirmed to "FAIL (Red phase)" before implementation. Integration-First says "Prefer real databases over mocks" and "Contract tests mandatory before implementation" — [Spec Kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).
- **Claude Code:** "If it has nothing to run that tells it whether the work actually *is* done, 'looks done' is all it has to go on. In practice that makes you the test suite." An example prompt: "write a failing test that reproduces it, then fix it" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- **Devin (search extract):** the playbook "Specifications" section lists postconditions Devin checks at the end. These are written per playbook, so they can carry fixed expected outcomes — [Devin: Creating playbooks](https://docs.devin.ai/product-guides/creating-playbooks).

### Inferences
- For domain rules with fixed reference values (e.g. "rate X yields Y for input Z"), properties alone are too weak: a property can hold while the constants are wrong. Kiro itself falls back to example-based tests where properties don't map. Domain rules in the technical design could carry an explicit reference-example table that the harness turns into golden tests before implementation, as Spec Kit does with contract tests. These tests would also serve as ready-made "failing test" proofs for conformance findings.
- Spec Kit's red-first contract tests line up with our AC0: the AC0 interface (import, call shape, result keys) can be turned mechanically into a contract test that exists before the implementation diff. The conformance pass then no longer has to find interface drift from prose.

### Gaps
- I found no primary-source write-up on golden or reference-value tests specifically in agent spec workflows.
- I could not fetch Kiro's full correctness page to confirm how it treats numeric domain constants.

## 5. Any reported results on how well this works?

### Takeaway
Quantitative evidence is thin. The best-documented numbers come from Google's AutoCommenter, a reviewer of conformance to written practices, and I saw them only as secondary summaries because arXiv was blocked. Kiro and Spec Kit report anecdotes and adoption, not controlled results. Anthropic's guidance is qualitative and warns about over-eager reviewers.

### Cited Findings
- **Google AutoCommenter:** the authors conclude that a model that automatically learns language best practices "is feasible and has a measurable positive impact on the developer workflow", deployed to tens of thousands of developers — [Google Research publication page](https://research.google/pubs/ai-assisted-assessment-of-coding-practices-in-industrial-code-review/); [arXiv 2405.13565](https://arxiv.org/abs/2405.13565) (abstract via search extract).
- **AutoCommenter (secondary summaries only, not verified):** coverage of 68% of best practices frequently referenced by human reviewers in one summary, and 66% in another. Lessons: outdated rules (e.g. changed Python import guidance) needed to be suppressible without downtime, and non-actionable URLs and poor summaries hurt usefulness — [DX newsletter summary](https://newsletter.getdx.com/p/ai-assisted-code-reviews-at-google); conflicting figure in other secondary summaries (e.g. [emergentmind](https://www.emergentmind.com/papers/2405.13565)). Treat as unverified until checked against the paper.
- **Kiro (search extract):** a Kiro blog post reports that PBT "caught a security bug I never would have found" (anecdotal, single case) — [Kiro blog](https://kiro.dev/blog/property-based-testing-fixed-security-bug/).
- **Spec Kit:** adoption only (about 151k GitHub stars, 13.6k forks as of Nov 2026); no outcome metrics in the repo — [Spec Kit README](https://github.com/github/spec-kit).
- **Anthropic:** a reviewer asked to find problems "will always find *something*", and fixing every finding leads to "extra abstraction layers and tests for cases that can't happen" (qualitative) — [Claude Code best practices](https://code.claude.com/docs/en/best-practices). "human review remains crucial for ensuring solutions align with broader system requirements" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).
- **Separate industry study (not AutoCommenter; from a search extract of arXiv 2412.18531):** 73.8% of automated review comments were labeled resolved, but average PR closure time rose from 5h52m to 8h20m — [arXiv 2412.18531](https://arxiv.org/abs/2412.18531) (not fetched; verify).

### Inferences
- The AutoCommenter lessons (suppressing stale rules, actionable links back to the rule) support our design: requiring each finding to quote the spec makes it actionable and checkable, and design rules need versioning so stale rules don't produce findings.
- With no published precision data for spec-vs-diff reviewers, our own escape data (3 tickets with interface and domain deviations found only by humans) is a reasonable baseline. Logging dropped findings (no verbatim quote) and unproven findings (no failing test) would let us measure the precision/recall trade-off of each gate.

### Gaps
- Could not verify AutoCommenter's exact numbers from the paper (arXiv blocked). Secondary sources disagree (66% vs 68%).
- No controlled study found on Kiro, Spec Kit, Copilot, Claude Code or Devin spec-conformance effectiveness.
- No primary data found on Meta's AI code-review conformance systems within this budget.
