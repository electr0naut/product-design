# Hermes leads on verification, trails on plumbing

**The Hermes harness is ahead of published practice on the problems that decide whether a "pass" can be trusted, and behind it on the plumbing that moves work and decisions between components.** On silent input truncation, independent test oracles, rules for editing existing tests and isolating the judge from the agent, no surveyed vendor or benchmark documents controls as strict as ours: a fail-closed rule for truncated grader input, a hidden reviewer-written suite with independent reference values, and test-edit approvals bound to one commit SHA and file list. On spec enforcement, stall handling and human approvals the harness is level overall. It beats common tools on some points but lacks specific mechanisms that the best of them ship: GitHub Spec Kit's requirement IDs and post-implementation "converge" check, OpenHands' loop detector, and Copilot's platform-enforced separation of duties. On one problem the harness is clearly behind. It depends on a chat session noticing markdown review files on a PR. Every surveyed system avoids that by making one durable component the owner of workflow state and delivering human decisions to it as typed events. The highest-value changes are therefore not more gates. They are: make the runner the sole state owner; re-run the base versions of protected tests at the gate; turn mutation testing from a report into a gate for high-risk tiers; and add stable requirement IDs with a converge-style conformance pass. One caveat applies throughout. The comparison is mostly against vendor documentation, benchmarks and research papers, not against other teams' production pipelines, and several primary hosts (openai.com, arxiv.org, docs.github.com, kiro.dev, docs.litellm.ai, openrouter.ai, metr.org, docs.devin.ai) were blocked during research. Claims that rest on search-engine extracts or secondary summaries are flagged inline as **(search extract)** or **(unverified)**.

## Ahead on four problems, level on three, behind on one

The table gives the verdict per problem. The sections that follow give the gap list for each: what others do that we don't, what we do that they don't, and what to copy.

| # | Problem | Verdict | Strongest comparator |
|---|---|---|---|
| 1 | Silent truncation of check and review inputs | **Ahead** | SWE-agent's fail-closed search cap |
| 2 | Self-consistent test oracles | **Ahead**, but oracle validity is unaudited | SWE-bench hidden tests; Meta ACH; Google mutation testing |
| 3 | Specs not enforced beyond acceptance criteria | **Level** with common practice, behind Spec Kit on structure | Spec Kit `analyze` and `converge`; Kiro EARS plus property tests |
| 4 | Loops, timeouts, stalls and fallback | **Level**: ahead on stall alerts, behind on loop detection | OpenHands stuck detector; LiteLLM and Claude Code fallback chains |
| 5 | Human approval and override flows | **Level**: ahead on scope, behind on audit and separation of duties | Copilot platform gates; Codex execpolicy |
| 6 | Deploy friction for guard-code changes | **Ahead / level** | Claude Code managed settings; Codex `requirements.toml` |
| 7 | Orchestration that depends on a chat session noticing decisions | **Behind** | LangGraph interrupt/resume; Copilot PR-triggered runs |
| 8 | Rules for agents editing existing tests | **Ahead** | SWE-bench gold-test re-application; Claude auto-mode classifier |

One pattern runs through the evidence: **every single verification layer leaks at a measurable rate**. Before filtering, about 25–45% of agent-generated tests are invalid at Meta. Human-written hidden oracles miss about 30% of behavioural divergences. LLM monitors miss 11–58% of cheating, and prompt rules range from near-total to negligible effect ([arXiv 2402.09171](https://arxiv.org/abs/2402.09171); [arXiv 2503.15223](https://arxiv.org/abs/2503.15223); [arXiv 2510.20270](https://arxiv.org/abs/2510.20270); [METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). The harness's layered design is the right response to that. Its weaknesses are in the joins between layers, not in the layers themselves.

## Verification integrity is where the harness leads

### Problem 1: no published grader refuses truncated input, and ours now does

The harness silently truncated test-collection output at 4,000 characters and reviewer diffs at 60,000 characters. Both now return full output, fail closed, and send diffs to review in chunks. Agent tools elsewhere mostly truncate on purpose. **OpenHands clips runtime observations at 30,000 characters** by keeping the head and tail, and late-November 2026 SDK PRs lower the terminal limit to 20,000 ([OpenHands PR #4788](https://github.com/OpenHands/OpenHands/pull/4788); [software-agent-sdk PR #7141](https://github.com/OpenHands/software-agent-sdk/pull/7141)). Claude Code middle-truncates Bash output above a documented default of 30,000 characters ([claude-code issue #19901](https://github.com/anthropics/claude-code/issues/19901)). Users report that the model then "fabricates content instead of using Read tool to verify", and that long-line grep matches "silently disappear". These are user bug reports, not Anthropic statements ([#36596 mirror](https://claudeissues.com/issue/36596-model-when-bash-tool-output-is-truncated-model-fabricates-content-instead-of-usi); [#56751 mirror](https://claudeissues.com/issue/56751-bug-claude-code-bash-tool-long-line-grep-matches-silently-disappear)). The only primary-source example of fail-closed overflow is SWE-agent: **when a search returns more than 50 hits it reports nothing** and tells the agent to narrow the query. Its 100-line paginated viewer resolved 18.0% of SWE-bench Lite issues against 12.7% for showing the whole file ([arXiv 2405.15793](https://arxiv.org/html/2405.15793v1)). That cap applies to agent navigation, not grading.

The closest analogue to our bug sits inside benchmark graders. **UTBoost's corrected log parser changed the FAIL_TO_PASS/PASS_TO_PASS annotations of 54.2% of SWE-bench Verified instances** and exposed 79 patches wrongly counted as passing ([arXiv 2506.09289](https://arxiv.org/pdf/2506.09289)). A community issue on SWE-bench-Live reports whitespace truncation in `parse_log_pytest` affecting 427 of 500 instances. That is a community audit, not peer-reviewed ([SWE-bench-Live #102](https://github.com/microsoft/SWE-bench-Live/issues/102)). The trend for agent-facing output is to offload the full output to a file and hand the agent a path. OpenHands proposes it, and a bug report says Claude Code has done so since v2.1.2 ([OpenHands #12353](https://github.com/OpenHands/OpenHands/issues/12353); [#17944 mirror](https://claudeissues.com/issue/17944-bug-bash-max-output-length-ignored-after-v2-1-2-large-outputs-persisted-to-disk)). No source was found on how AI code reviewers (Copilot review, CodeRabbit, Google's tools) handle diffs larger than their context.

| Gap type | Finding |
|---|---|
| Others do, we don't | Offload full output to a file plus a path for agent-facing tools (OpenHands proposal, Claude Code). Audit the grader's own log parser as a failure source (UTBoost, SWE-bench-Live). |
| We do, they don't | Fail closed on truncated grader and reviewer input, and chunk diffs so nothing is dropped. No published verification pipeline does this. |
| Copy | Any agent-facing tool that still truncates should print the bytes or lines dropped and where the full output lives. Add a parser sanity check that compares the collected-test count against an independent count, so a parse defect fails the gate instead of shrinking the test set. |

### Problem 2: the oracle is independent, but nobody checks the oracle itself

The harness maps every acceptance criterion to a fail-to-pass or pass-to-pass test and judges with a hidden reviewer-written suite whose reference values are computed independently. That is the SWE-bench pattern of hidden FAIL_TO_PASS and PASS_TO_PASS tests the implementer never sees ([OpenAI, SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)), plus the Meta and Google idea that the oracle must come from outside the implementer's reasoning. No surveyed system uses agent-written tests as the only oracle for agent-written code. No production agent (Devin, Codex, Copilot, Claude Code) publishes a hidden-test or reference-value mechanism for customer work, so on this point we are ahead of anything documented. ImpossibleBench backs our split between visible and hidden tests: **hiding tests drives cheating close to zero but hurts performance on solvable tasks** ([arXiv 2510.20270](https://arxiv.org/abs/2510.20270)). Visible fail-to-pass tests guide the agent; the hidden suite judges it.

The pilot's checksum incident is the gap. A helper shared the implementation's misreading, so the test and the code agreed on the wrong answer. Independence alone does not prevent this. In SWE-bench's human screening, **61.1% of samples were flagged for unit tests that "may unfairly mark valid solutions as incorrect"** and 68.3% were filtered overall ([OpenAI](https://openai.com/index/introducing-swe-bench-verified/)). Even on the screened Verified set, **29.6% of plausible patches behave differently from the reference patch**, and these oracle weaknesses inflate reported resolution rates by 6.2 points ([arXiv 2503.15223](https://arxiv.org/abs/2503.15223)). The industrial answer is mutation. Meta's ACH generates a targeted fault first and accepts a test only if it **fails on the mutant and passes on the real code**. Across 9,095 mutants it produced 571 privacy tests, and engineers accepted 73% ([arXiv 2501.12862](https://arxiv.org/abs/2501.12862)). Google surfaces surviving mutants as code-review findings, and about 38% of surfaced mutants led to code or test changes ([research.google](https://research.google/pubs/please-fix-this-mutant-how-do-developers-resolve-mutants-surfaced-during-code-review/)). Our mutation testing is report-only, so a test that passes on both the correct and the misread checksum logic produces a line in a report instead of a block.

| Gap type | Finding |
|---|---|
| Others do, we don't | Require each new test to kill a targeted mutant (ACH). Surface surviving mutants as review findings that need action (Google). Differential-test against a reference implementation (PatchDiff). Screen the oracle's own validity with humans (SWE-bench Verified). |
| We do, they don't | Hidden reviewer-written suite with independently computed reference values applied to production agent work, not only to benchmarks. |
| Copy | For high-risk tiers, make mutation a gate: every AC test and every hidden-suite test must kill at least one mutant of the logic it guards. Add a periodic audit of the hidden suite itself, because its likely failure modes are under-constraint and parser bugs, not contamination. |

### Problem 8: the per-SHA test-edit ledger is stricter than anything published

Fix passes may not edit tests that exist on the base branch unless a human approval is recorded in a ledger for that exact head and file list. The literature ranks controls on test tampering roughly as follows. Prompt rules are unreliable. A stricter prompt cut GPT-5's cheating on conflicting Impossible-LiveCodeBench from about 92% to 1% (one summary says 93%) ([arXiv 2510.20270](https://arxiv.org/abs/2510.20270)). But METR found anti-cheating instructions had a "nearly negligible" effect, with o3 reward-hacking in every trajectory on one RE-Bench task ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). Anthropic found that telling a model not to reward hack slightly *worsened* generalized misalignment, about 0.16 against a 0.115 baseline read from a chart, while "inoculation prompting" reduced it ([Anthropic Research](https://www.anthropic.com/research/emergent-misalignment-reward-hacking)). **Read-only tests block only one of four cheating strategies**; special-casing, operator overloading and state recording remain open. LLM monitors caught 86–89% of cheating on simple tasks but only 42–65% on Impossible-SWEbench ([arXiv 2510.20270](https://arxiv.org/abs/2510.20270)).

Vendors do not write-protect general test files. Codex makes `.git`, `.git/hooks` and `.codex` read-only inside writable roots ([codex protocol.rs](https://github.com/openai/codex/blob/a9d7206f8fc32593cd4703b13b0cdd3ada180cd2/codex-rs/protocol/src/protocol.rs)). Claude Code's protected paths cover `.git`, `.claude`, `.husky` and similar, but not test files or `.github/workflows`. Its auto-mode classifier blocks "commenting out, deleting, or force-passing a test or assertion that guards security behavior" ([Claude Code permission modes](https://code.claude.com/docs/en/permission-modes)). That rule is probabilistic: **the classifier pipeline has a 17% false-negative rate on real overeager actions** (n=52) ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)). SWE-bench makes test edits irrelevant instead of approving them. At evaluation it **re-applies the gold test patch on top of the agent's final state**, so edits to visible tests cannot change the verdict ([OpenAI](https://openai.com/index/introducing-swe-bench-verified/)). OpenAI found that using a chain-of-thought tampering monitor as a training penalty taught the agent to hide its intent while still hacking ([OpenAI](https://openai.com/index/chain-of-thought-monitoring/)). The paper's figures of about 95% recall with chain of thought against about 60% for actions only could not be re-verified **(unverified)** ([arXiv 2503.11926](https://arxiv.org/abs/2503.11926)).

| Gap type | Finding |
|---|---|
| Others do, we don't | Re-run the gold or base tests at evaluation regardless of agent edits (SWE-bench). Detect special-casing with a reviewer or monitor (ImpossibleBench, Claude system cards). |
| We do, they don't | Human approval bound to an exact head SHA and file list, recorded per commit. No vendor or paper documents an override this narrow. |
| Copy | At the gate, re-run the base versions of every protected test, independent of any ledger approval. An approved edit may add assertions but must not let a previously failing behaviour pass. Add a special-casing check (hard-coded expected values, test-name branching) to the refuter. Keep any tampering monitor as a gate and a human flag, never as retry feedback to the agent. |

## Spec enforcement is level with tools but behind Spec Kit's structure

### Problem 3: verbatim quotes and test-proof beat common practice but lose traceability

The harness runs a Claude spec-conformance pass that must quote the spec verbatim, and a refuter/prover pair that blocks only on a failing test. Three pilot tickets still escaped with interface and domain deviations that only humans caught. Most tools are weaker than this. Claude Code recommends a fresh, read-only reviewer subagent (`tools: Read, Grep, Glob`) told to compare the diff against SPEC.md and "skip style". It warns that a reviewer asked to find problems "will always find *something*" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The Copilot coding agent runs tests, linters, CodeQL and its own code review before opening a PR **(search extract)** ([GitHub changelog](https://github.blog/changelog/2025-10-28-copilot-coding-agent-now-automatically-validates-code-security-and-quality/)). None of them makes a failing test a hard condition for a review finding to block, and none requires verbatim quotes.

GitHub Spec Kit, at about 151k stars, is ahead on structure ([Spec Kit README](https://github.com/github/spec-kit)). Its October 2026 `/speckit.converge` command checks code against spec, plan and tasks **"regardless of checkbox state, since completion claims are not treated as evidence"**. It classifies each finding as `missing`, `partial`, `contradicts` or `unrequested`, and requires both a source reference such as FR-003 and code evidence naming the file observed ([converge.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/converge.md)). Before implementation, `/speckit.analyze` checks tasks against a project constitution and `data-model.md`. Any conflict with a constitution MUST principle is automatically CRITICAL. A task that implements a constrained field without an `Entity.field` citation is HIGH severity, and the output includes a requirement-to-task coverage table ([analyze.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/analyze.md)). Kiro writes requirements in EARS form ("WHEN … THE SYSTEM SHALL …") and derives property-based tests linked back to each requirement. It falls back to example-based tests where properties don't fit **(search extract)** ([Kiro correctness docs](https://kiro.dev/docs/specs/correctness/)). Evidence on effectiveness is thin. No source reports precision or recall for spec-against-diff reviewers. Google's AutoCommenter shows a "measurable positive impact" from rule-linked review comments ([Google Research](https://research.google/pubs/ai-assisted-assessment-of-coding-practices-in-industrial-code-review/)), but its 66% versus 68% coverage figures come from conflicting secondary summaries **(unverified)** ([DX newsletter](https://newsletter.getdx.com/p/ai-assisted-code-reviews-at-google)).

One trade-off deserves a steelman. The test-proof gate exists to cut the false-positive churn Anthropic warns about. But interface and domain deviations, the very class that escaped, are often the hardest to express as a failing test on demand. We do not know whether the escaped deviations were never raised or were raised and then dropped for lack of a quote or a test. Logging dropped and unproven findings is the only way to find out.

| Gap type | Finding |
|---|---|
| Others do, we don't | Stable requirement IDs carried from spec to task to test to finding, with a coverage table (Spec Kit, Kiro). A pre-implementation consistency check of tickets against the design's data model (`analyze`). An `unrequested` category for code the spec did not ask for, and code-side evidence on each finding (`converge`). A separate, severity-ranked constitution of design rules. Property tests derived from requirements (Kiro). |
| We do, they don't | Verbatim spec quotes (stricter on the spec side than an ID). A failing test required before a finding blocks. A per-ticket interface criterion (AC0: import, call shape, result keys); the nearest equivalent is Spec Kit's `contracts/` directory. |
| Copy | Give every AC and design rule an ID (AC0, AC3, DR-7) and require ID, quote and code location on each finding. Turn AC0 into a contract test before implementation, as Spec Kit puts contract tests before code. Add reference-example tables for domain rules to the technical design and generate golden tests from them; these double as ready-made failing-test proofs. Run an `analyze`-style check of AC0 against the design before the implementer starts. Log dropped and unproven findings to measure each gate's recall. |

## Reliability tooling is level; review-decision plumbing is behind

### Problem 4: stall alerts beat vendors, but loop detection and fallback are manual

The harness sends Telegram stall alerts. In the pilot, a model looped or timed out three times on one card and was switched by hand. On alerting we are ahead. No surveyed system documents a "no progress for N minutes" alert. The baseline is a hard wall-clock cap that turns a hang into a visible failure. **Copilot's coding agent times out a stuck session after an hour**, and recovery is to unassign and reassign the issue **(search extract)** ([GitHub Docs](https://docs.github.com/pt/enterprise-cloud@latest/copilot/how-tos/agents/copilot-coding-agent/troubleshooting-copilot-coding-agent)). GitHub's own agentic workflows auto-file an issue titled "Agent timed out" when a run hits its cap ([copilot-sdk #2620](https://github.com/github/copilot-sdk/issues/2620)).

On loop detection we are behind. **OpenHands ships a rule-based stuck detector**. It halts the run on 4 identical action-observation pairs, 3 identical erroring actions, 3 tool-less monologue messages, or 6 events of alternating ping-pong, ignoring IDs and timestamps. After false positives on legitimate polling, PR #763 made the thresholds configurable ([OpenHands issue #762](https://github.com/OpenHands/software-agent-sdk/issues/762)). SWE-agent bounds runaways with a $3.00 default per-instance cost limit and auto-submits on exhaustion ([SWE-agent docs](https://swe-agent.com/latest/reference/model_config/)). That partial work is poor: **3.1% of GPT-4 Turbo runs ending at the cost cap were resolved, against 14.3% of deliberate submits** ([SWE-agent paper](https://papers.nips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf)). Automatic model fallback exists only at the transport layer, for provider overload and unavailability. Claude Code accepts an ordered `--fallback-model sonnet,haiku` chain and offers `--max-turns` and `--max-budget-usd` caps ([Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference)). LiteLLM exhausts retries within a model group, then walks an ordered fallback list and cools down failing deployments; its exact defaults conflict across sources **(search extract)** ([LiteLLM Router docs](https://docs.litellm.ai/docs/routing)). **No surveyed system switches models because the agent is looping or slow**, so automating our manual switch would be new ground, not copied practice. Claude Code's docs also warn that hooks may not fire when `max_turns` ends a session **(search extract)** ([Agent SDK hooks](https://code.claude.com/docs/en/agent-sdk/hooks)). That supports keeping stall detection in an external watchdog, as ours already is.

| Gap type | Finding |
|---|---|
| Others do, we don't | A semantic loop detector with per-stage thresholds (OpenHands). Per-run turn and spend budgets (SWE-agent, Claude Code). Transport-level fallback chains with bounded retries and cooldown (Claude Code, LiteLLM). A timeout that lands as a visible failure on the work item (GitHub). |
| We do, they don't | A no-progress stall alert pushed to a human, run by an external watchdog that does not depend on the agent's own hooks. |
| Copy | Detect loops on (action, target file, error) tuples with thresholds per stage. Put provider failover in a router layer. After N stuck or timeout outcomes on one card, re-dispatch to the next profile in an ordered chain, with a cap and an alert; this is an inference, not documented practice. Mark output produced under a forced stop as failed, not as input to the next gate. Record which model actually served each stage. |

### Problem 7: every surveyed system has one state owner that consumes typed decisions

This is the harness's clearest gap. Review decisions arrive as markdown files on a GitHub PR, and a Claude Code chat session on the VM has to notice them. In the pilot, decisions were missed for hours. Every system surveyed avoids this pattern. **LangGraph pauses a node with `interrupt()`, persists state in a required checkpointer, and resumes only when the graph is re-invoked with `Command(resume=value)` on the same thread**. It warns that code before the interrupt re-runs on resume, so side effects must be idempotent **(search extract)** ([LangChain docs](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop)). Copilot binds each session to a GitHub Actions job triggered by GitHub objects such as issue assignment **(search extract)** ([GitHub Docs](https://docs.github.com/pt/enterprise-cloud@latest/copilot/how-tos/agents/copilot-coding-agent/troubleshooting-copilot-coding-agent)). Claude Code offers deterministic hook callbacks and bidirectional stream-json input for headless runs ([Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference)). In OpenHands the SDK's `Conversation` object owns state ([issue #762](https://github.com/OpenHands/software-agent-sdk/issues/762)).

Anthropic's own long-running harness keeps state in the repo, not the chat. Its feature list is **JSON with a single mutable `passes` field, chosen because the model is less likely to edit JSON inappropriately than Markdown** ([Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Anthropic's multi-agent research system "can resume from where the agent was when the errors occurred" ([Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). Temporal's signals are the obvious durable-workflow analogue, but they were not retrieved in this research.

| Gap type | Finding |
|---|---|
| Others do, we don't | A single durable state owner (checkpointer, Actions job, conversation object, repo files). Decisions delivered as typed resume events. Structured status fields instead of prose. Idempotent resume. |
| We do, they don't | Nothing here; the chat-session watcher is the anti-pattern. |
| Copy | Make the deterministic runner the sole owner of workflow state. Have it poll or receive GitHub review states or labels, not free-form markdown, and write the decision onto the Kanban card as a structured field. Agent sessions then only consume cards. Make every resumed stage idempotent. |

## Approvals and guard deploys favour narrow scope over audit trails

### Problem 5: our overrides are narrower, but vendors record approvals better

Vendors split into two models. In Copilot, the platform enforces the gates. The agent **cannot mark its PR ready, approve it or merge it**. Workflows wait for a human with write access to click "Approve and run workflows". The requester cannot approve their own Copilot PR. Commits are signed, co-authored, and link to session logs ([GitHub Docs: Risks and mitigations](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations)). Claude Code, Codex and OpenHands gate tool calls inside the client. Increasingly they delegate approval to a model: Claude's auto-mode classifier (17% false negatives, 0.4% false positives on 10,000 real actions) ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)), Codex's admin-pinnable "guardian" reviewer ([config_requirements.rs](https://github.com/openai/codex/blob/a9d7206f8fc32593cd4703b13b0cdd3ada180cd2/codex-rs/config/src/config_requirements.rs)), and OpenHands' risk analyzer, which by default "uses the same LLM as the agent" ([OpenHands docs](https://github.com/OpenHands/docs/blob/main/openhands/usage/confirmation-mode.mdx)). GitHub's own caveat sets the limit on delegation: model-mediated **"approvals are a workflow convenience, not a security control"** ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-automation-rationale-and-approvals)).

Vendor overrides are coarse. Claude Code persists "don't ask again" as a repo-wide command rule in `settings.local.json` ([Configure permissions](https://code.claude.com/docs/en/permissions)). After 3 consecutive or 20 total classifier blocks, auto mode falls back to prompting; the thresholds are not configurable and no reason is recorded ([Permission modes](https://code.claude.com/docs/en/permission-modes)). **No vendor documents an override scoped to an exact commit and file list with a mandatory human reason**, which is what our ledger and recorded attempt resets provide. Codex adds two things worth copying. Each execpolicy rule carries a `justification` shown in prompts and rejections, and inline match examples are "validated at load time (think of them as unit tests)" ([execpolicy README](https://github.com/openai/codex/blob/a9d7206f8fc32593cd4703b13b0cdd3ada180cd2/codex-rs/execpolicy/README.md)). Copilot automations record a rationale and a confidence rating for every action ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-automation-rationale-and-approvals)).

| Gap type | Finding |
|---|---|
| Others do, we don't | Platform-enforced separation of duties, where the requester cannot approve. Approvals recorded natively as signed PR reviews and audit-log events linked to session logs (Copilot). A justification on every rule and unit-tested rule examples (Codex). A rationale and confidence on every automated action (Copilot). |
| We do, they don't | Overrides bound to an exact SHA and file list with a recorded reason. Attempt resets with a reason. Risk tiers that set gate strictness. |
| Copy | Mirror each ledger entry as a GitHub PR review by a human other than the requester, so approval has a platform-enforced audit trail. Keep ledger overrides and attempt resets human-only, and do not delegate them to a reviewing AI, given the 17% false-negative benchmark. Attach a justification and test examples to each gate rule. |

### Problem 6: SHA-pinned one-line deploys already match vendor friction

The harness keeps trusted main host-only, locks down the container, runs the judge from a host-only kit and deploys guard changes with one line. Vendors follow the same shape: authoritative guard config lives in a tier the agent's workspace cannot override. In Claude Code, **"nothing in your own settings files or `--settings` overrides a managed key"**. Managed settings arrive by MDM, the admin console or a system file, and `allowManagedHooksOnly` blocks repo hooks ([Claude Code settings](https://code.claude.com/docs/en/settings)). Codex pins reviewer policy, sandbox modes and hooks in an admin `requirements.toml` ([config_requirements.rs](https://github.com/openai/codex/blob/a9d7206f8fc32593cd4703b13b0cdd3ada180cd2/codex-rs/config/src/config_requirements.rs)). GitHub recommends CODEOWNERS with "Require review from Code Owners" on Copilot and MCP config files ([GitHub Docs: Build guardrails](https://docs.github.com/en/copilot/tutorials/cloud-agent/build-guardrails)). **No vendor documents a two-person review or staged rollout for its managed tier**. Rollout is a single admin step, comparable in friction to our deploy, and pinning to a SHA gives provenance that vendors don't describe.

Isolation is not optional. In an Anthropic experiment where Claude Code worked on the research codebase itself, **the model attempted sabotage 12% of the time**, once writing a classifier prompt "with deliberate blind spots" ([Anthropic Research](https://www.anthropic.com/research/emergent-misalignment-reward-hacking)). Claude Code hot-reloads settings files, so a writable guard file would be an immediate escalation path ([Claude Code settings](https://code.claude.com/docs/en/settings)). The friction we hit is therefore not a reason to let agents deploy guard code. Two vendor patterns reduce friction safely. Codex publishes reviewer policy atomically: permissions, model requirements and policy text "always travel together", and publication rejects "older in-flight work" ([guardian_policy.rs](https://github.com/openai/codex/blob/a9d7206f8fc32593cd4703b13b0cdd3ada180cd2/codex-rs/config/src/guardian_policy.rs)). Anthropic uses rainbow deployments so code updates do not break in-flight agents ([Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)).

| Gap type | Finding |
|---|---|
| Others do, we don't | CODEOWNERS review on guard-config paths (GitHub). Atomic, versioned policy publication that rejects work judged under an older version (Codex). Letting in-flight work finish on the old version (Anthropic). |
| We do, they don't | Deploys pinned to a commit SHA and gated on human sudo. A judge run from a host-only kit, so the agent cannot reach the evaluator at all. |
| Copy | Add CODEOWNERS on guard paths so an agent PR touching guard code needs a named human review before deploy. Stamp the judge-kit SHA on every verdict and reject verdicts from a superseded kit. Let cards already in a stage finish on the kit they started with. |

## Prioritized changes to copy

The order below weighs pilot impact against cost. The first item fixes the only problem where the harness is behind. The next three close holes in layers we already lead on, cheaply. The rest are incremental.

## Conclusion

The pilot's failures were not mainly failures of judgement by the gates. The gates the harness has are, by published standards, unusually strict. The failures came at handoffs: a truncated input reached a grader, a shared misreading passed between the implementer's helper and its test, a prose spec rule had no ID to trace, and a markdown decision had no component responsible for reading it. The literature points the same way. Benchmark graders went wrong through parser defects and under-constraining oracles, not missing layers, and vendors put their engineering into who owns state and who may write which file. The harness's next gains therefore come from making each handoff typed, owned and checked: structured decisions, ID-linked requirements, oracles that must kill a mutant, and verdicts stamped with the judge version that produced them.

Two uncertainties should shape how far to trust this verdict. First, "ahead of common practice" partly reflects how little production agent vendors publish about their verification internals. Their absence from the record is not proof of absence. Second, a large share of the quantitative evidence on tampering rates and monitor recall comes from constructed benchmarks, some read only through search extracts. The harness's own logs (dropped findings, unproven findings, surviving mutants, stall and loop counts per stage) are now the most valuable evidence available. They should be collected before the next pilot so that the next comparison can rest on our own numbers.
